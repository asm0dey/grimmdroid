# Built-in EPUB Reader Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Read EPUBs inside Grimmdroid with Readium, keeping position and bookmarks in sync with Grimmory (and, through Grimmory, KOReader).

**Architecture:** A separate `ReaderActivity` (a `FragmentActivity`, because Readium's navigator is a Fragment) hosts `EpubNavigatorFragment` under Compose chrome. Grimmory speaks EPUB CFI and Readium speaks `Locator`, so a pure-JVM `reader/cfi` package (jsoup over the EPUB zip) translates between them. Local Room tables hold the phone's position, pending uploads and bookmarks; `PositionSync` applies the "furthest wins, ask before jumping, never overwrite further-ahead" rules; WorkManager sends what couldn't be sent offline.

**Tech Stack:** Kotlin 2.4, Compose Material 3, Readium Kotlin Toolkit 3.4.0 (`readium-shared`, `readium-streamer`, `readium-navigator`), jsoup, Ktor 3.6, Room 2.8, DataStore, WorkManager, kotest + Robolectric + Ktor MockEngine.

**Spec:** `docs/superpowers/specs/2026-10-19-reader-design.md`

## Global Constraints

- EPUB only in the reader; every other format keeps today's buttons and behaviour.
- minSdk 26, compileSdk/targetSdk 37, Java 21 bytecode. New dependencies pinned to exact versions in `gradle/libs.versions.toml`.
- Grimmory endpoints are relative paths on the authed client (`api/v1/...`), like `GrimmoryApi` today.
- Server positions: `epubProgress.percentage` and uploaded `progressPercent` are **0–100**; `koreaderProgress.percentage` is a **0–1 fraction** (verify in Task 13; adjust one constant if not).
- "Same place" tolerance: two total progressions within **0.005** of each other are equal (my call, ≈1 page of a 200-page book).
- Upload debounce: **3 s** after the last locator change, plus immediately on `onStop` (my call).
- Never jump without a tap. Never upload over a further-ahead server position unless the user chose **Make this position current**. Never move the user backwards automatically.
- Do not trust `epubProgress.href`. A CFI that cannot be resolved falls back to the percentage, never to the start of the book.
- No device name or age in the jump bar: "Further ahead on another device: 60% — Jump"; percentage-only targets say "about 60%".
- Reader settings live on the phone (DataStore file `reader`), apply to every book, never sync to the server.
- Multi-account: every position, pending upload, bookmark and server font is keyed by `accountId`.
- No production interface whose only purpose is testability; tests fake HTTP with Ktor `MockEngine` and the fake fails the test on unexpected requests.
- Every new source file carries the GPL header used by existing files.
- Test command: `./gradlew :app:testDebugUnitTest --tests '<fqcn>'`; full gate before each commit: `./gradlew :app:testDebugUnitTest :app:lintDebug spotlessCheck`.

## Review Focus

1. **Range CFIs from foliate-js** (`epubcfi(/6/8!/4/2,/2/1:0,/40/1:120)`): must resolve to the range *start*, not fail. Test in Task 2.
2. **CFIs that point into text nodes or carry `[id]` assertions / index past the end** (book edited on the server): must fall back to the nearest element, then to percentage. Test in Task 3.
3. **Upload racing a held-back state**: the user ignores Jump, reads on, leaves; the worker later finds the server *still* ahead and must keep holding, not upload. Test in Task 6.
4. **Account switch / sign-out while the reader is open or an upload is pending**: pending rows for a removed account must be dropped, not sent with another account's client. Test in Task 6.
5. **Server returns 403 for custom fonts** (user lacks the "manage fonts" permission): treat as "no server fonts", no error shown. Test in Task 12.

**Interfaces:**

- Produces:
  - `sealed interface ServerPosition { val totalProgression: Double }` with `data class Exact(target: PositionTarget, cfi: String, totalProgression: Double)` and `data class Approximate(totalProgression: Double)`
  - `fun serverPosition(dto: BookProgressDto, archive: EpubArchive): ServerPosition?` — Exact when the CFI resolves (`totalProgression = percentage / 100`); else Approximate from `epubProgress.percentage / 100`; KOReader's fraction is used when it is **further** than the epub percentage (it is only ever *offered*, never auto-applied); null when nothing is there.
  - `sealed interface OpenDecision { data object Stay; data class OpenAt(p: ServerPosition); data class OfferJump(p: ServerPosition) }`
  - `fun decideOnOpen(local: Double?, server: ServerPosition?): OpenDecision` — local null & server non-null → `OpenAt`; server ahead by > 0.005 → `OfferJump`; else `Stay`.
  - `fun decideOnSyncNow(local: Double, server: ServerPosition?): OpenDecision` — `OfferJump` whenever the difference exceeds 0.005, either direction.
  - `class PositionSync(dao: ReaderDao, api: suspend (accountId: Long) -> GrimmoryApi, enqueue: (accountId: Long) -> Unit)`:
    - `suspend fun saveLocal(accountId: Long, bookId: Long, locatorJson: String, totalProgression: Double)` — upsert with `pending = NORMAL` (keeps FORCE if already FORCE)
    - `suspend fun makeCurrent(accountId: Long, bookId: Long)` — set `pending = FORCE`, then `upload`
    - `suspend fun upload(accountId: Long, bookId: Long, bookFileId: Long, cfi: () -> String?): UploadResult` — `enum class UploadResult { SENT, HELD_BACK, FAILED }`. NORMAL: GET server first; server ahead by > 0.005 → `HELD_BACK`, row stays `NORMAL`. FORCE or not ahead: PUT `progressPercent = totalProgression * 100`, `positionData = cfi()`, `positionHref` = locator href; on success `pending = NONE`. IO error → `FAILED`, row unchanged, `enqueue(accountId)`.
  - `PositionUploadWorker` (CoroutineWorker, network constraint, unique work per account `"pos-upload-$accountId"`, exponential backoff): for each pending row of its account, opens the downloaded file's `EpubArchive` (from `DownloadRepository`) and calls `upload`; HELD_BACK counts as done for the worker (only the next reading session or a manual action changes it); account gone → delete rows, `Result.success()`.
